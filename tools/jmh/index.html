    JMH: Java Microbenchmark Harness¶

    L3 · ✅ the project below was built and run on JDK 21 (4 vCPU); the numbers are real

    Hand-written timing loops lie, because of JIT warm-up, dead-code elimination, constant folding, and GC noise. JMH (from the OpenJDK team) handles all of that: separate forked JVMs, warm-up iterations, blackholes, and statistics with error bars.

    Project: examples/tools-lab/jmh

    cd examples/tools-lab/jmh
mvn package                                   # builds target/benchmarks.jar (shaded, main = org.openjdk.jmh.Main)
java -jar target/benchmarks.jar -l            # list benchmarks
java -jar target/benchmarks.jar CounterBenchmark
java -jar target/benchmarks.jar ExecutorBenchmark -prof gc
java -jar target/benchmarks.jar -h            # all options

    Benchmark 1: contended counters¶

    Four threads increment one shared counter. @State(Scope.Group) plus @Group/@GroupThreads(4) is the JMH way of saying "these 4 threads share this state".

    CounterBenchmark.java
    package com.playbook.jmh;

import org.openjdk.jmh.annotations.Benchmark;
import org.openjdk.jmh.annotations.BenchmarkMode;
import org.openjdk.jmh.annotations.Fork;
import org.openjdk.jmh.annotations.Group;
import org.openjdk.jmh.annotations.GroupThreads;
import org.openjdk.jmh.annotations.Measurement;
import org.openjdk.jmh.annotations.Mode;
import org.openjdk.jmh.annotations.OutputTimeUnit;
import org.openjdk.jmh.annotations.Scope;
import org.openjdk.jmh.annotations.State;
import org.openjdk.jmh.annotations.Warmup;

import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.atomic.LongAdder;
import java.util.concurrent.locks.ReentrantLock;

/**
 * Four threads increment ONE shared counter as fast as they can. Which counter scales under contention?
 * Run: java -jar target/benchmarks.jar CounterBenchmark
 */
@State(Scope.Group)                                  // one counter instance shared by the 4 threads of a group
@BenchmarkMode(Mode.Throughput)
@OutputTimeUnit(TimeUnit.MICROSECONDS)
@Warmup(iterations = 3, time = 1)
@Measurement(iterations = 5, time = 1)
@Fork(1)
public class CounterBenchmark {

    private long syncCounter;
    private final Object monitor = new Object();
    private long lockCounter;
    private final ReentrantLock lock = new ReentrantLock();
    private final AtomicLong atomic = new AtomicLong();
    private final LongAdder adder = new LongAdder();

    @Benchmark @Group("synchronized") @GroupThreads(4)
    public long synchronizedIncrement() {
        synchronized (monitor) { return ++syncCounter; }
    }

    @Benchmark @Group("reentrantLock") @GroupThreads(4)
    public long reentrantLockIncrement() {
        lock.lock();
        try { return ++lockCounter; } finally { lock.unlock(); }
    }

    @Benchmark @Group("atomicLong") @GroupThreads(4)
    public long atomicIncrement() {
        return atomic.incrementAndGet();               // returned → JMH consumes it, no dead-code elimination
    }

    @Benchmark @Group("longAdder") @GroupThreads(4)
    public void adderIncrement() {
        adder.increment();                              // side effect on shared state is enough
    }
}

    Result (real):

    Benchmark                        Mode  Cnt    Score    Error   Units
CounterBenchmark.atomicLong     thrpt    5   52.478 ±  9.634  ops/us
CounterBenchmark.longAdder      thrpt    5  365.815 ± 17.587  ops/us
CounterBenchmark.reentrantLock  thrpt    5   20.521 ±  1.747  ops/us
CounterBenchmark.synchronized   thrpt    5    9.759 ±  2.024  ops/us
    xychart-beta title "4 threads, one shared counter (ops per microsecond, higher is better)" x-axis ["synchronized", "ReentrantLock", "AtomicLong", "LongAdder"] y-axis "ops/us" 0 --> 400 bar [9.8, 20.5, 52.5, 365.8]

    What it teaches:

    • LongAdder is 7× faster than AtomicLong and 37× faster than synchronized under contention. Each thread mostly updates its own striped cell, while AtomicLong makes every CAS fight over one cache line.
    • Locks pay for parking and waking threads. ReentrantLock beat synchronized here, but that varies with JDK version and contention. Measure your case; don't quote a rule.
    • LongAdder.sum() isn't an atomic snapshot, so for IDs or sequence numbers you still need AtomicLong.

    Benchmark 2: platform pool vs virtual threads¶

    One "request" fans out N blocking 10 ms calls and waits for all of them. @Param runs the benchmark for each fan-out size.

    ExecutorBenchmark.java
    package com.playbook.jmh;

import org.openjdk.jmh.annotations.Benchmark;
import org.openjdk.jmh.annotations.BenchmarkMode;
import org.openjdk.jmh.annotations.Fork;
import org.openjdk.jmh.annotations.Level;
import org.openjdk.jmh.annotations.Measurement;
import org.openjdk.jmh.annotations.Mode;
import org.openjdk.jmh.annotations.OutputTimeUnit;
import org.openjdk.jmh.annotations.Param;
import org.openjdk.jmh.annotations.Scope;
import org.openjdk.jmh.annotations.Setup;
import org.openjdk.jmh.annotations.State;
import org.openjdk.jmh.annotations.TearDown;
import org.openjdk.jmh.annotations.Warmup;

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;

/**
 * One "request" = fan out N blocking IO calls (10 ms each) and wait for all. Average time per request.
 * Platform pool of 200 vs a new virtual thread per call.
 * Run: java -jar target/benchmarks.jar ExecutorBenchmark
 */
@State(Scope.Benchmark)
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.MILLISECONDS)
@Warmup(iterations = 2, time = 2)
@Measurement(iterations = 3, time = 2)
@Fork(1)
public class ExecutorBenchmark {

    @Param({"100", "1000"})
    int fanOut;

    ExecutorService platformPool;

    @Setup(Level.Trial)
    public void setUp() { platformPool = Executors.newFixedThreadPool(200); }

    @TearDown(Level.Trial)
    public void tearDown() { platformPool.close(); }

    static int blockingIo() throws InterruptedException {
        Thread.sleep(10);
        return 1;
    }

    @Benchmark
    public int platformPool200() throws Exception {
        return fanOut(platformPool);
    }

    @Benchmark
    public int virtualThreads() throws Exception {
        try (var vt = Executors.newVirtualThreadPerTaskExecutor()) {
            return fanOut(vt);
        }
    }

    private int fanOut(ExecutorService ex) throws Exception {
        List<Future<Integer>> fs = new ArrayList<>(fanOut);
        for (int i = 0; i < fanOut; i++) fs.add(ex.submit(ExecutorBenchmark::blockingIo));
        int sum = 0;
        for (Future<Integer> f : fs) sum += f.get();
        return sum;
    }
}

    Result (real, -prof gc):

    Benchmark                                             (fanOut)  Mode  Cnt       Score        Error   Units
ExecutorBenchmark.platformPool200                          100  avgt    3      12.573 ±      7.813   ms/op
ExecutorBenchmark.platformPool200:gc.alloc.rate.norm       100  avgt    3   10410.562 ±  10895.122    B/op
ExecutorBenchmark.platformPool200                         1000  avgt    3      54.354 ±      6.576   ms/op
ExecutorBenchmark.platformPool200:gc.alloc.rate.norm      1000  avgt    3   74973.388 ±  41761.902    B/op
ExecutorBenchmark.virtualThreads                           100  avgt    3      10.548 ±      0.915   ms/op
ExecutorBenchmark.virtualThreads:gc.alloc.rate.norm        100  avgt    3   79290.425 ±    181.851    B/op
ExecutorBenchmark.virtualThreads                          1000  avgt    3      11.099 ±      1.063   ms/op
ExecutorBenchmark.virtualThreads:gc.alloc.rate.norm       1000  avgt    3  855716.386 ± 511178.041    B/op
    Fan-out Pool(200) Virtual threads Why
    100 12.6 ms 10.5 ms Both fit: 100 < 200 threads, so the time ≈ one 10 ms call
    1,000 54.4 ms 11.1 ms The pool runs 1000/200 = 5 waves × 10 ms. VTs all wait at once

    -prof gc shows the cost: virtual threads allocate about 79 KB per 100 tasks, or ~800 bytes per virtual thread (thread object + continuation + stack chunks). The pool reuses threads and allocates far less. That's the honest trade-off: VTs swap threads (an OS-limited resource) for heap allocation (which the GC handles cheaply). It's the reason you don't create VTs for nanosecond-sized CPU tasks.

    The rules that make benchmarks correct¶

    Rule In the code
    Return the result or use a Blackhole, or the JIT deletes the work Methods return long/int
    Use @State for inputs (not constants), or the JIT folds them Counters live in the state object
    Fork at least once (@Fork(1)) so profiles from other benchmarks don't leak in @Fork(1)
    Warm up @Warmup(iterations = 3)
    Read the error column: overlapping intervals mean "no proven difference" ±
    Test contention explicitly @GroupThreads(4), @Threads(n), or -t 4
    Look at allocation, not only time -prof gc
    Check what was actually compiled -prof perfasm (Linux, needs hsdis)

    Useful command-line options¶

    java -jar target/benchmarks.jar CounterBenchmark -f 3 -wi 5 -i 10      # 3 forks, 5 warmups, 10 measurements
java -jar target/benchmarks.jar ExecutorBenchmark -p fanOut=10000      # override a @Param
java -jar target/benchmarks.jar -t 8 SomeBenchmark                     # 8 threads
java -jar target/benchmarks.jar -rf json -rff results.json             # machine-readable (jmh.morethan.io visualizes it)
java -jar target/benchmarks.jar -prof stack                            # where benchmark threads spend time (incl. waiting)
