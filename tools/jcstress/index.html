    jcstress: Testing the Java Memory Model¶

    L3 L4 · ✅ the project below was built and run on JDK 21 (x86-64, 4 vCPU); the numbers are real

    Normal unit tests can't prove the absence of a race: the bad interleaving might happen once in a billion runs. jcstress (OpenJDK's concurrency stress harness) runs tiny "actor" methods concurrently hundreds of millions of times across JVM configurations, records every outcome, and classifies each one as acceptable, interesting, or forbidden.

    Project: examples/tools-lab/jcstress

    cd examples/tools-lab/jcstress
mvn package                                         # target/jcstress.jar
java -jar target/jcstress.jar -m quick              # all tests, quick mode (~ minutes)
java -jar target/jcstress.jar -t StoreBuffering     # tests matching a regex
java -jar target/jcstress.jar -m default            # longer, more samples
# HTML report: results/index.html

    How a jcstress test works¶

    sequenceDiagram participant H as jcstress harness participant S as fresh @State object participant A1 as @Actor 1 (thread 1) participant A2 as @Actor 2 (thread 2) participant R as Result (e.g. II_Result) loop hundreds of millions of times H->>S: new State() par concurrently A1->>S: x = 1, then read y into r1 A2->>S: y = 1, then read x into r2 end H->>R: record (r1, r2), e.g. "0, 0" end H->>H: histogram vs @Outcome rules → OK / FAILED

    Test 1: store buffering (can both threads miss each other's write?)¶

    StoreBufferingTest.java
    package com.playbook.jcstress;

import org.openjdk.jcstress.annotations.Actor;
import org.openjdk.jcstress.annotations.JCStressTest;
import org.openjdk.jcstress.annotations.Outcome;
import org.openjdk.jcstress.annotations.State;
import org.openjdk.jcstress.infra.results.II_Result;

import static org.openjdk.jcstress.annotations.Expect.ACCEPTABLE;
import static org.openjdk.jcstress.annotations.Expect.ACCEPTABLE_INTERESTING;
import static org.openjdk.jcstress.annotations.Expect.FORBIDDEN;

/** Dekker-style store buffering. Can both threads miss each other's write? */
public class StoreBufferingTest {

    @JCStressTest
    @Outcome(id = {"0, 1", "1, 0", "1, 1"}, expect = ACCEPTABLE, desc = "some interleaving")
    @Outcome(id = "0, 0", expect = ACCEPTABLE_INTERESTING, desc = "both reads before both writes: REORDERING")
    @State
    public static class Plain {
        int x, y;
        @Actor public void actor1(II_Result r) { x = 1; r.r1 = y; }
        @Actor public void actor2(II_Result r) { y = 1; r.r2 = x; }
    }

    @JCStressTest
    @Outcome(id = {"0, 1", "1, 0", "1, 1"}, expect = ACCEPTABLE, desc = "some interleaving")
    @Outcome(id = "0, 0", expect = FORBIDDEN, desc = "volatile forbids this (sequential consistency)")
    @State
    public static class Volatile {
        volatile int x, y;
        @Actor public void actor1(II_Result r) { x = 1; r.r1 = y; }
        @Actor public void actor2(II_Result r) { y = 1; r.r2 = x; }
    }
}

    Result (real):

    .......... [OK] com.playbook.jcstress.StoreBufferingTest.Plain
  RESULT     SAMPLES     FREQ       EXPECT  DESCRIPTION
    0, 0  65,240,364   31.94%  Interesting  both reads before both writes: REORDERING
    0, 1  76,684,689   37.54%   Acceptable  some interleaving
    1, 0  62,338,738   30.52%   Acceptable  some interleaving
    1, 1       2,818   <0.01%   Acceptable  some interleaving

    0, 0 is impossible under any interleaving of the source code, yet it happened 65 million times (32%). Each CPU's write sat in its store buffer while it read the other variable from cache. Even x86, with its strong memory model, allows this one reordering. The Volatile variant declares 0, 0 FORBIDDEN and passed: volatile inserts the store-load fence.

    Test 2: lost update (volatile is not atomic)¶

    LostUpdateTest.java
    package com.playbook.jcstress;

import org.openjdk.jcstress.annotations.Actor;
import org.openjdk.jcstress.annotations.Arbiter;
import org.openjdk.jcstress.annotations.JCStressTest;
import org.openjdk.jcstress.annotations.Outcome;
import org.openjdk.jcstress.annotations.State;
import org.openjdk.jcstress.infra.results.I_Result;

import java.util.concurrent.atomic.AtomicInteger;

import static org.openjdk.jcstress.annotations.Expect.ACCEPTABLE;
import static org.openjdk.jcstress.annotations.Expect.ACCEPTABLE_INTERESTING;
import static org.openjdk.jcstress.annotations.Expect.FORBIDDEN;

/** Two threads each do one increment. The @Arbiter runs after both and records the final value. */
public class LostUpdateTest {

    @JCStressTest
    @Outcome(id = "2", expect = ACCEPTABLE, desc = "both increments counted")
    @Outcome(id = "1", expect = ACCEPTABLE_INTERESTING, desc = "LOST UPDATE: count++ is read-modify-write")
    @State
    public static class VolatilePlusPlus {
        volatile int count;                       // volatile does NOT make ++ atomic
        @Actor public void actor1() { count++; }
        @Actor public void actor2() { count++; }
        @Arbiter public void arbiter(I_Result r) { r.r1 = count; }
    }

    @JCStressTest
    @Outcome(id = "2", expect = ACCEPTABLE, desc = "both increments counted")
    @Outcome(id = "1", expect = FORBIDDEN, desc = "impossible with CAS")
    @State
    public static class Atomic {
        final AtomicInteger count = new AtomicInteger();
        @Actor public void actor1() { count.incrementAndGet(); }
        @Actor public void actor2() { count.incrementAndGet(); }
        @Arbiter public void arbiter(I_Result r) { r.r1 = count.get(); }
    }
}

    Result (real):

    .......... [OK] com.playbook.jcstress.LostUpdateTest.VolatilePlusPlus
  RESULT      SAMPLES     FREQ       EXPECT  DESCRIPTION
       1    9,166,492    4.17%  Interesting  LOST UPDATE: count++ is read-modify-write
       2  210,751,002   95.83%   Acceptable  both increments counted

    Two increments produced 1 in 9 million runs. @Arbiter runs after both actors finish and records the final state. The Atomic variant (CAS) declares 1 forbidden and passed.

    Test 3: unsafe publication (plain vs final fields)¶

    UnsafePublicationTest.java
    package com.playbook.jcstress;

import org.openjdk.jcstress.annotations.Actor;
import org.openjdk.jcstress.annotations.JCStressTest;
import org.openjdk.jcstress.annotations.Outcome;
import org.openjdk.jcstress.annotations.State;
import org.openjdk.jcstress.infra.results.I_Result;

import static org.openjdk.jcstress.annotations.Expect.ACCEPTABLE;
import static org.openjdk.jcstress.annotations.Expect.ACCEPTABLE_INTERESTING;
import static org.openjdk.jcstress.annotations.Expect.FORBIDDEN;

/** Can a reader see a published object whose constructor-written field is still 0? */
public class UnsafePublicationTest {

    static class Holder {
        int value;                                     // NOT final
        Holder() { value = 42; }
    }

    static class FinalHolder {
        final int value;                               // final-field semantics (JLS 17.5)
        FinalHolder() { value = 42; }
    }

    @JCStressTest
    @Outcome(id = "-1", expect = ACCEPTABLE, desc = "not published yet")
    @Outcome(id = "42", expect = ACCEPTABLE, desc = "fully initialized")
    @Outcome(id = "0", expect = ACCEPTABLE_INTERESTING, desc = "saw the object but NOT its field: unsafe publication")
    @State
    public static class PlainField {
        Holder h;                                      // plain field: racy publication
        @Actor public void writer() { h = new Holder(); }
        @Actor public void reader(I_Result r) { Holder l = h; r.r1 = (l == null) ? -1 : l.value; }
    }

    @JCStressTest
    @Outcome(id = "-1", expect = ACCEPTABLE, desc = "not published yet")
    @Outcome(id = "42", expect = ACCEPTABLE, desc = "fully initialized")
    @Outcome(id = "0", expect = FORBIDDEN, desc = "final fields are always visible once the reference is")
    @State
    public static class FinalField {
        FinalHolder h;
        @Actor public void writer() { h = new FinalHolder(); }
        @Actor public void reader(I_Result r) { FinalHolder l = h; r.r1 = (l == null) ? -1 : l.value; }
    }
}

    On this x86 machine, the 0 outcome (the reference is visible but the field isn't) wasn't observed. x86 doesn't reorder stores with other stores, so the constructor's write becomes visible before the reference. The JMM still allows it, and on ARM (AWS Graviton, Apple Silicon, many phones) it can show up. This is the lesson of jcstress: "it passed on my laptop" proves nothing about the memory model. Run memory-model tests on the architectures you deploy to.

    Outcome annotations cheat sheet¶

    Expect Meaning Use for
    ACCEPTABLE Allowed and expected Normal interleavings
    ACCEPTABLE_INTERESTING Allowed by the JMM, but surprising Documenting reorderings you want to see
    ACCEPTABLE_SPEC Allowed by the spec, rarely seen in practice Edge cases
    FORBIDDEN The test fails if it's ever seen Asserting your synchronization works

    Result types: I_Result, II_Result, JJ_Result, Z_Result, L_Result, … (field r1, r2, … of the given types). Other annotations: @Arbiter (runs after the actors), and @JCStressTest(Mode.Termination) with a @Signal method (to test that a spinning thread can be stopped, e.g. that a stop flag needs volatile).
