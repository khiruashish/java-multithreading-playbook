    14. Bank Transfer¶

    L2 ★★☆ · ordered locking · consistent snapshot

    Problem¶

    Implement transfer(from, to, amount) for a bank with many accounts and thousands of concurrent transfers. Requirements: no lost updates, no negative balances, no deadlock, and the total money in the bank never changes, even when you audit it while transfers are running.

    Key idea¶

    • A lock per account gives fine-grained concurrency (transfers between unrelated accounts run in parallel).
    • A transfer needs two locks, so a deadlock is possible (A→B concurrently with B→A). Lock in id order.
    • "Check balance, then debit" is a check-then-act, so it's safe only while both locks are held.
    • The audit locks all accounts in the same id order to get a consistent snapshot.
    sequenceDiagram participant T1 as transfer(A→B) participant LA as lock A (id 1) participant LB as lock B (id 2) participant T2 as transfer(B→A) T1->>LA: lock (lower id first) T2--xLA: lock A first too → waits T1->>LB: lock T1->>T1: check & move money T1->>LB: unlock T1->>LA: unlock T2->>LA: acquires A, then B → proceeds

    Code walkthrough¶

    Account¶

        static final class Account {
        private final long id;
        private final ReentrantLock lock = new ReentrantLock();
        private long balanceMinor;                       // guarded by lock

        Account(long id, long openingMinor) { this.id = id; this.balanceMinor = openingMinor; }

        long balance() {
            lock.lock();
            try { return balanceMinor; } finally { lock.unlock(); }
        }
    }

    The balance is a long in minor units (paise or cents). Never use double for money: 0.1 + 0.2 != 0.3.

    Transfer¶

        static final AtomicLong rejected = new AtomicLong();

    /** @return true if moved, false if insufficient funds */
    static boolean transfer(Account from, Account to, long amountMinor) {
        if (amountMinor <= 0) throw new IllegalArgumentException("amount must be positive");
        if (from == to) return true;                     // same lock twice would be fine (reentrant) but pointless

        Account first = from.id < to.id ? from : to;     // global lock order by id → no deadlock cycle
        Account second = first == from ? to : from;

        first.lock.lock();
        try {
            second.lock.lock();
            try {
                if (from.balanceMinor < amountMinor) {   // check-then-act is SAFE: both locks are held
                    rejected.incrementAndGet();
                    return false;
                }
                from.balanceMinor -= amountMinor;
                to.balanceMinor += amountMinor;
                return true;
            } finally {
                second.lock.unlock();
            }
        } finally {
            first.lock.unlock();
        }
    }
    Code Why
    amountMinor <= 0 check Validate input before taking any lock.
    if (from == to) return true; Avoids locking the same account twice. It would work (the lock is reentrant), but it's pointless.
    first = from.id < to.id ? from : to Global lock ordering, which removes the circular wait. Ids are unique and stable, unlike identityHashCode.
    Balance check inside both locks No other thread can change either balance between the check and the update.
    Nested try/finally Each lock is released even if the inner code throws, in reverse acquisition order.

    Audit¶

        /** Consistent snapshot of the total: lock ALL accounts in id order, then sum. */
    static long auditTotal(Account[] accounts) {
        for (Account a : accounts) a.lock.lock();        // accounts[] is sorted by id
        try {
            long total = 0;
            for (Account a : accounts) total += a.balanceMinor;
            return total;
        } finally {
            for (int i = accounts.length - 1; i >= 0; i--) accounts[i].lock.unlock();
        }
    }

    Summing balances without locks can read A before a transfer and B after it, which double-counts the money in flight. Locking every account (in id order, so it can't deadlock with transfers) gives a moment where no transfer is half-done.

    flowchart LR subgraph Unlocked sum a1[read A = 100] --> t[transfer A→B 50 happens] --> b1[read B = 150] --> s1[total off by +50] end subgraph Locked audit a2[lock A..Z in id order] --> s2[sum] --> u[unlock] --> ok[exact total] end

    Run it¶

    200,000 concurrent random transfers on virtual threads, with an audit in the middle of the run:

    200,000 concurrent transfers: total before=5000000 after=5000000 mid-run audit=5000000, rejected(insufficient)=4400
PASS

    Follow-up questions¶

    The audit blocks all transfers. Can you avoid that?

    Yes, with MVCC or snapshots: keep an append-only ledger (double-entry: every transfer writes −amount and +amount entries in one atomic step), then compute balances as of a ledger position. That's how real wallets and DBs work.

    What about across many service instances?

    In-JVM locks don't help there. Use one DB transaction with SELECT … FOR UPDATE on both rows in id order, or optimistic @Version with retries, plus an idempotency key per transfer. See Distributed Concurrency.

    Could you use synchronized instead of ReentrantLock?

    Yes: synchronized (first) { synchronized (second) { … } }. On JDK 21–23 that's fine because nothing blocks inside (pure memory updates). ReentrantLock adds tryLock if you want timeouts.

    Full source: BankTransfer.java 
    import java.util.concurrent.Executors;
import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.locks.ReentrantLock;

/**
 * Thread-safe money transfer between accounts: no lost updates, no deadlock, total money conserved.
 * Money is held in minor units (paise) as long — never double.
 * Run: java BankTransfer.java
 */
public class BankTransfer {

    static final class Account {
        private final long id;
        private final ReentrantLock lock = new ReentrantLock();
        private long balanceMinor;                       // guarded by lock

        Account(long id, long openingMinor) { this.id = id; this.balanceMinor = openingMinor; }

        long balance() {
            lock.lock();
            try { return balanceMinor; } finally { lock.unlock(); }
        }
    }

    static final AtomicLong rejected = new AtomicLong();

    /** @return true if moved, false if insufficient funds */
    static boolean transfer(Account from, Account to, long amountMinor) {
        if (amountMinor <= 0) throw new IllegalArgumentException("amount must be positive");
        if (from == to) return true;                     // same lock twice would be fine (reentrant) but pointless

        Account first = from.id < to.id ? from : to;     // global lock order by id → no deadlock cycle
        Account second = first == from ? to : from;

        first.lock.lock();
        try {
            second.lock.lock();
            try {
                if (from.balanceMinor < amountMinor) {   // check-then-act is SAFE: both locks are held
                    rejected.incrementAndGet();
                    return false;
                }
                from.balanceMinor -= amountMinor;
                to.balanceMinor += amountMinor;
                return true;
            } finally {
                second.lock.unlock();
            }
        } finally {
            first.lock.unlock();
        }
    }

    /** Consistent snapshot of the total: lock ALL accounts in id order, then sum. */
    static long auditTotal(Account[] accounts) {
        for (Account a : accounts) a.lock.lock();        // accounts[] is sorted by id
        try {
            long total = 0;
            for (Account a : accounts) total += a.balanceMinor;
            return total;
        } finally {
            for (int i = accounts.length - 1; i >= 0; i--) accounts[i].lock.unlock();
        }
    }

    public static void main(String[] args) throws Exception {
        int n = 50;
        Account[] accounts = new Account[n];
        for (int i = 0; i < n; i++) accounts[i] = new Account(i, 1_000_00);    // ₹1,000.00 each
        long before = auditTotal(accounts);

        long[] midAudit = new long[1];
        try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int t = 0; t < 200_000; t++) {
                ex.submit(() -> {
                    var rnd = ThreadLocalRandom.current();
                    transfer(accounts[rnd.nextInt(n)], accounts[rnd.nextInt(n)], rnd.nextLong(1, 50_00));
                });
                if (t == 100_000) ex.submit(() -> midAudit[0] = auditTotal(accounts));
            }
        }
        long after = auditTotal(accounts);
        System.out.printf("200,000 concurrent transfers: total before=%d after=%d mid-run audit=%d, rejected(insufficient)=%d%n",
                before, after, midAudit[0], rejected.get());
        if (before != after || midAudit[0] != before) throw new AssertionError("money created or destroyed!");
        for (Account a : accounts) if (a.balance() < 0) throw new AssertionError("negative balance");
        System.out.println("PASS");
    }
}
